# 象棋助手 v2（重写版）

> 基于 YOLOv8 / ONNX Runtime 的棋盘识别 + 皮卡鱼引擎分析。
> 本仓库是 `outputs/xiangqi-assistant` 的**重写**，不是修补。
> 生成日期：2026-10-17。

## 一、为什么重写

旧项目不是"模型不够强"，而是**把已经拿到的信息扔掉了**。

它的 `detector.onnx` 是一个 15 类检测器（红黑各 7 种棋子 + 棋盘），
`[1,25200,20]` 的输出里**类别和位置是同源的**。但产线只取框的位置：

```
找盘 → 裁片 → YOLO 检子（只用位置）→ 90 格逐格分类（7 类）→ 墨色判红黑 → 剪枝/校准/复核
```

于是凭空多出两个不可靠环节，后面所有补丁都在修它们带来的病：

| 现象 | 旧项目的补丁 | 真正的病根 |
|---|---|---|
| 仕被认成马 | `cropSideRatio` 从 1.1 调到 0.88 | 单格分类器对裁片尺度没有裕度 |
| 木纹棋盘幻影棋子 | `CellSolidFilter` + `OverlimitSilenceRecheck` | 分类器把背景纹理当棋子，而它是"有没有子"的唯一权威 |
| 红黑判反 | `InkSideResolver` 取样框吸附 | 14 类模型已经给了阵营，却改用墨色重判 |
| 棋盘两端串列 | `GridFitter` 反推真实格距 | 格距来自「框宽/9」，而框宽实际是 7.95~8.36 个列距 |
| 出招要等 3 秒 | 补耗时日志定位 | 1 次找盘 + 1 次检子 + 最多 90 次小推理，残局还要重跑一遍整图 |

`core/rule/` 下 7 个模块（`StructuralPruner` / `TypeBudgetRepair` / `OpeningCalibration` /
`OverlimitSilenceRecheck` / `StepResolver` …）全是这套链路的**补救**，不是象棋本身的需求。

## 二、新链路

```
截屏帧 → letterbox → YOLO 一次推理 → 框+类别
                                    ├→ 棋盘框：只用来限定格距搜索范围
                                    └→ 棋子框中心：一维周期拟合求格距/相位 → 吸附交点 → 组装盘面
                                                                                    → Pikafish 分析
```

四个决定性差异：

1. **类别不再丢**。棋子种类来自检测模型，红黑同源，没有第二个分类器、没有墨色判据。
2. **几何不猜**。格距由棋子框中心自己拟合（棋子就站在格点上，这是最强的几何证据），
   不用「框宽/9」反推 —— 实测框宽是 7.95~8.36 个列距，按 9 算会低估 13%。
3. **没有"修盘面"**。冲突取最高分、超限按分数裁掉，不需要知道象棋规则。
4. **一次推理**。每帧只有一次神经网络调用，耗时从"秒级不确定"变成"一次推理 + 两次一维搜索"。

## 三、已验证的精度

**5 张真实截图（JJ象棋 / 另一款教学 App），160 个棋子，逐格 100% 正确。**

验收方式：逐张人工读图登记真值（`tools/truth.tsv`），与组装结果逐格对比。
命令：

```bash
python tools/assemble_fit.py \
  --model ../xiangqi-assistant/app/src/main/assets/detector.onnx \
  --images ../xiangqi-training/labeled_opening/*.jpg ../xiangqi-training/labeled_opening/*.png \
  --truth truth.tsv --out ../out
```

三组对照数据（同一批图、同一个模型，只改一处）：

| 改动 | 逐格正确率 | 说明 |
|---|---|---|
| 旧产线预处理：直接拉伸 640 | — | 35 个检出，红方出现 4 个"马"、7 个"兵"，中位置信 0.763 |
| 改 letterbox | — | 33 个检出，黑方 16/16 全对，中位置信 **0.930** |
| 按「框宽/9」推格距 | 91.3%（39/450 错） | 落盘只有 21~25 子，残差 0.3~0.4 格 |
| 改为周期拟合格距 | 98.2%（8/450 错） | 落盘 32 子，残差 0.005~0.09 格 |
| 登记真值后复核 | **100%（0/450 错）** | 那 8 格是"真值假设"错了，不是识别错 |

> 最后一步要说明白：98.2% → 100% **不是算法改进**，是验收基准错了。
> `labeled_opening` 目录名叫"开局"，但其中 4 张的红相已经走到中路（教学提示态），
> 按"开局=固定阵型"去比，必然差 2 格。这同时说明旧项目的
> `OpeningCalibration`（确认"32 交点与开局一致"就直接按坐标给棋子）在真实教学界面上会误判。

## 六之二、真实截图验收（19 张 JJ象棋）

数据在 `testsets/jj-real/`：19 张同一局对战的真实截图（64强战），开局到残局全覆盖，
其中 2 张是红方在上（界面换边）。

### 最关键的结论

| 模型 | 5 张有人工真值 | 19 张真实对局 | 吸附残差 | 检出 : 落盘 |
|---|---|---|---|---|
| 旧 **v5** `detector.onnx` | **100%（450/450 格）** | **19/19 通过强约束** | 0.069~0.141 | 有 2~13 个重复框 |
| **yolov8n 纯合成**（3000 张） | 86.7% | **只有 11/19** | 0.02~0.09 | 严重漏检，10~32 |
| **yolov8n 微调**（合成 + 24 真实伪标签） | **100%（450/450 格）** | **19/19 通过强约束** | **0.015~0.025** | **几乎 1:1** |

两条硬结论：

1. **纯合成数据训出的模型在真实 JJ象棋 画面上不可用。** 合成图是 PIL 画的平面木纹 + 汉字，
   真机是 3D 立体棋子 + 光影 + 装饰，域差异太大。合成数据能「打通管线」，**不能替代真实数据**。
2. **24 张真实截图的伪标签微调，就把它从 86.7% 拉回 100%**，还顺手消掉了 v5 那些重复框
   （残差改善 4 倍）。说明「伪标签 → 微调」这条路是通的，缺的只是**更多真实截图**。

### 三道独立验证（19 张真实对局）

这批图没有逐张人工真值，用三道互相独立的证据交叉确认：

1. **两个独立训练的模型逐格完全一致 19/19 张**——旧 v5（他人训练）和微调后的 yolov8n，
   架构、训练数据、训练流程全都不同，1710 格一格里都没有分歧；
2. **19/19 通过象棋强约束**（`tools/fen_lint.py`）：将帅在位且列 4 / 行 0 或 9、士象只能在自己的
   绝对合法点位上、兵卒不在己方底线、各类子数不超限；
3. **人工抽检 3 张**（黑在上 / 残局 / 红在上）逐颗核对，零错误。

真值登记在 `testsets/jj-real/truth.tsv`，两个模型跑出来都是 **0 格错 / 1710 格**。

### 修掉的真 bug：锚定不能用 min 平移

周期拟合的相位只是「模格距的等价类」。旧版用「检出格坐标的最小行/列」当 0 位移——
一旦最外列或最上行恰好没有棋子（中局残局极常见），整个盘面就整体错位一整列/行。
19 张实测：越界格 13~20 个/张。

改用**象棋规则锚定**（`RulesAnchor`）：在候选偏移里搜一个让盘面最合法的偏移。约束只用规则，
不依赖皮肤：将帅必在列 4、必在行 0/9 且相差 9 行；士象必与己方将同半区；兵卒不倒退；子数不超限。
→ 越界降到 0~1 个/张，19 张锚定值完全一致。

> 也试过「棋盘框中心 == (列 4.03, 行 4.47)」直接取整：19 张真实图都成立，
> 但会让 `3f95e43b` 错一整行。**几何假设不够，必须叠规则约束。**

### 附带发现

- 棋盘外的误检有固定形态：玩家头像、右下"沙盘"按钮这些**圆形**元素会被认成黑「炮」，
  吸附后落到行 -3 / 行 11。锚定后越界即丢弃，不影响盘面。
- v5 每张有 2~13 个**重复检测**（同一棋子出两个大小不同的框，IoU 低躲过 NMS）。
  靠吸附后的同格冲突消解按置信取一，结果不受影响。**微调后的模型没有这个问题。**

## 六之三、真实域微调

`tools/pseudo_label.py` 用已验证的 v5 给真实图打 YOLO 伪标签。
过滤策略是关键：**只保留「吸附到合法格点且参与最终盘面」的框**，
于是棋盘外的圆形误检自动被丢掉，不需要额外规则。

- 24 张（19 真实 + 5 真值图）全部成功，每张 22~32 子 + 1 个棋盘框
- 混合集 `D:/datasets/xiangqi-mix`：3000 合成 + 24 真实 ×8 副本（1:125 的比例信号会被淹没）
- 微调参数：从 `best.pt` 续训 30 轮，`lr0=0.004`、`lrf=0.05`、`fliplr=0`（镜像会破坏楚河汉界语义）
- `yaml` 里 `train` 必须写成 **YAML 列表**；逗号分隔的字符串会被当成单个路径而报错

## 六之四、49 张残局截图：微调模型反而退化了

新增 49 张 JJ象棋**残局闯关**截图（`D:/date/微信图片_*.jpg`，1280×2816）。
与之前那批不同：子少（3~33 个）、两种皮肤（灰石 + 木纹）、大量高亮圈标记
（绿色可走点、红色将军提示、白色选中点）、棋盘上方还有装饰棋子立牌。

| 模型 | 锚定方式 | FEN 强约束通过 |
|---|---|---|
| yolov8n 微调 | 棋规锚定 | 23/49 |
| yolov8n 微调 | 框中心锚定 | 23/49 |
| 旧 xqlink v5 | 棋规锚定 | 38/49 |
| 旧 **xqlink v5** | **框中心锚定** | **49/49** |

三个发现，按重要性排序：

**1. 微调模型在这批图上退化，v5 没有。** 两者在旧 19 张上都是 100%（1710/1710 格），
所以微调并没有「学到」，只是把 19 张的渲染特征记住了——换到残局+木纹皮肤就掉。
**当前该用 v5**，等真实数据够了再重训 v8。

**2. 锚定必须用棋盘框，不能靠棋规搜索。** 49 张里棋盘框全部检出（置信 0.97）、每张只有 1 个，
框中心恒等于格坐标 (4, 4.5)。而棋规锚定在残局上大面积失效：子少、帅已经离开中线、
将甚至漏检，搜出来的偏移会整体错 1~2 格，错位后连将都被挤出棋盘，
表现为「黑将缺失」——这是之前 11 张「无解」的真正原因。
框中心直接解整数平移（`BoardBoxAnchor`），49/49 全对。

**3. 拟合前必须先裁到棋盘框。** 棋盘上方的装饰棋子立牌、下方的被吃子托盘都是合法棋子外观，
检测器会稳定检出，离棋盘中心 3~6 个格距，混进周期拟合会把 pitch / phase 一起带偏。

另外修了 `tools/fen_lint.py` 两处**过严**约束：帅将可以走九宫的列 3/4/5、行 1/2 也合法，
早期写成「必须列 4、行 0 或 9」，把合法残局误判成错。修完 v5 的通过数从 22 涨到 38（锚定前）。


## 六之五、这 49 张的逐格真值定下来了

「49/49 通过强约束」只证明盘面合法，不证明每颗子都对。现在给这 49 张建了逐格真值，
放在 `testsets/jj-endgame/`（`truth.tsv` + `img/`，1099 颗子）。

**不靠模型分类建 GT 的做法**（`tools/gt_build.py`）：同一款 App 同一套皮肤里，棋子精灵是
像素级一致的，而模型错的基本都是分类、定位很准（吸附残差 0.01~0.05 格、棋盘框 0.97 置信）。
所以把问题拆开：

1. **定位**：两个模型（旧 xqlink / 自训 v8）的检出求并集 → 提高召回；假阳性交给第 2 步剔除。
2. **分类**：格中心裁 0.6 格距小块 → 「偏红 or 偏暗」的墨迹掩码 → 按墨迹重心整数平移对齐
   → 24×24 下采样 → 无监督聚类（阈值 0.80 → 117 簇）。每簇只让人眼看一次代表图就能定类。

**四道自动审计**（都能独立否掉人工定类）：

| 审计 | 手段 | 结果 |
|---|---|---|
| 簇纯净度 | 每簇看 4 个样本 | 117/117 纯净 |
| 墨色一致 | 红/黑字必须与标签大小写吻合 | 0 处冲突（揪出 2 处人工标错） |
| 棋规合法 | `fen_lint.py` 强约束 | 49/49 |
| **漏检出** | 3301 个「两模型都说空」的格子 vs 全部棋子簇心 | 最高相似度 **0.49**（真漏子会是 0.95+）→ 无整颗漏检 |

再加人工逐格核对 4 张（52/64/82/98，覆盖两种皮肤、开局型与残局型），零错。

**在这份真值上的成绩**（`tools/eval_gt.py`）：

| 模型 | 逐颗准确 | 查全 | 漏子 | 多子 | 整盘全对 |
|---|---|---|---|---|---|
| 旧 **xqlink v5** | **1099/1099 = 100%** | 100% | 0 | 0 | **49/49** |
| 自训 yolov8n 微调 | 811/1099 = 73.8% | 90.2% | 88 | 0 | 1/49 |

v8 的错误集中在 `b→c`(象→砲) 28、`R→漏`(俥) 25、`R→P` 19、`N→C` 13、`R→B` 11——
正是「字形相近 + 木纹皮肤」这类系统性混淆，不是随机噪声。

⚠️ **偏置说明（既不夸大也不低估）**：格子的「有/无子」由两模型并集定，而并集恰好等于
xqlink 的结果，所以 xqlink 的**漏检数是被构造出来的 0，不是测出来的**。但另外两项是实打的：

- 假阳性被人工剥掉了（2 个簇整体判空 + 1 个簇对黑墨色判空），所以「多子」是测出来的；
- 漏检另由像素相似度审计独立兜住（3301 个空格子最高 0.49，不看任何模型），所以漏检≈0 有独立支撑。

结论：xqlink 的 100% 里，**分类是真测的，多子是真测的，只有「漏检 0」这一项不该当成模型能力**。
这份真值测其它模型（含重训的 v8）完全没有这个偏置。

顺带得到一个明确结论：**v5 的分类头是好的**，旧项目的问题不在模型，在拉伸预处理 +
min 平移锚定。之前判断「v5 的 15 类输出被浪费」说的是老链路没用上它，不是它不准。

## 六之六、为什么「旧版实测不准」和「xqlink 49/49」不矛盾

用户实测旧 App 识别不准，但这里用同一份 `detector.onnx` 测出 100%。原因很简单：
**测的是权重，用的是产品**。旧 App 把这份权重放进了另一条链路 —— 四处都不同：

| 环节 | 旧 App（`xiangqi-assistant`） | 现链路 |
|---|---|---|
| 预处理 | `ImageOps.fitSquare` = `createScaledBitmap(bmp, 640, 640)`：整帧 1280×2816 **硬拉成正方形**（纵向压 2.2×），裁片再拉一次 | letterbox，保比例补灰边 |
| 落盘 | `BinnedGridMapper` 写死 `columnSpan=9 / rowSpan=11 / phase 0,0.5`，**完全不拟合** | 周期拟合格距相位 + 棋盘框中心定整数偏移 |
| 分类 | **`cell_classifier.onnx`（64×64 输入，只有 8 类输出）+ `InkSideResolver` 判红黑**，`readings` 非空就覆盖检测头 | 检测头自带的 15 类直接用 |
| 修补 | 7 个模块（`OverlimitSilenceRecheck` / `StructuralPruner` / `OpeningCalibration` / `TypeBudgetRepair` …） | 无 |

**最要命的是第三行**：旧 App 里 15 类检测头只是**兜底**。8 类 = 将/士/象/马/车/炮/兵/空，
**它本身分不出红黑**，红黑靠墨色启发式。所以「不准」的主体是那个小分类器加几何，不是 xqlink。

`tools/old_pipeline_ab.py` 把旧链路原样复现后做了消融（49 张残局、1099 颗）：

| 链路 | 逐颗正确 | 漏 | 多 | 整盘全对 |
|---|---|---|---|---|
| 旧 App 原样（拉伸 + 写死分箱） | 89.4% | 72 | 30 | **36/49** |
| letterbox + 写死分箱（混搭对照） | 97.3% | 0 | 0 | 27/49 |
| 现链路（letterbox + 拟合 + 框锚定） | **100%** | 0 | 0 | **49/49** |

两点必须说清：
- 89.4% 是旧链路的**上限** —— 它用的还是 15 类检测头；真实旧版用 8 类分类器，只会更差。
- 更要看「整盘全对」那一列：13 张盘面错 = 13 次错误 FEN = 13 次错误建议。
  逐颗 89% 的观感其实是「每盘都有一点不对」。



## 六之七、Android 外壳与引擎接线

识别层之外的东西，全部在这一节。目标是一句话：**开着悬浮窗打 JJ象棋，它自己看出盘面并建议下一手。**

### 组成

| 模块 | 文件 | 职责 |
|---|---|---|
| 抓屏 | `capture/FrameSource.kt`、`capture/AccessibilityFrameSource.kt`、`service/CaptureAccessibilityService.kt` | 无障碍 `takeScreenshot()`（API 30+），不需要每次授权 |
| 编排 | `pipeline/AnalysisPipeline.kt` | 帧 → 识别 → 合法性 → FEN → 引擎，唯一入口 |
| 盯盘循环 | `pipeline/BoardWatcher.kt` | 抓帧节奏、采纳门槛（可切多帧/单帧）、盘面没变不重算、走子方推断 |
| 引擎 | `engine/EngineLocator.kt` + `UciEngine.kt` | 皮卡鱼 2026-01-02 arm64 + 配套 NNUE，UCI 握手 → `go depth N movetime M` |
| 悬浮窗 | `service/OverlayService.kt` + `ui/OverlayViews.kt` | 胶囊悬浮球 + 展开面板，前台服务 `specialUse` |
| 主界面 | `MainActivity.kt` | 三项授权引导、引擎参数、本地图片分析 |
| 单例 | `XiangqiApp.kt` + `di/AppGraph.kt` | 模型会话与引擎进程是**应用级**资源，服务重启不重建 |

### 几个"代价换来的"决定

| 决定 | 为什么 |
|---|---|
| 引擎放 `jniLibs/` 而不是只放 `assets/` | Android 10 起应用不能执行自己可写目录里的文件（W^X）。`nativeLibraryDir` 是唯一带可执行权限的地方。所以 `useLegacyPackaging = true` 必须开，让系统把 `.so` 解压出来。 |
| 悬浮球做成**胶囊**，不是圆形棋子 | 无障碍截图拍的是合成后的整屏，会把自己的悬浮窗拍进去。深色圆盘 + 中间一个汉字，跟棋子几乎一样，落在格点上就会被检测成一颗子。圆角矩形不会。 |
| 面板展开时**暂停**盯盘 | 面板 300dp 宽，必然盖住棋盘，不暂停识别到的就是面板本身。收起后自动恢复；用户自己的暂停与这个是两个标志，互不覆盖。 |
| 连续 **2 帧**盘面完全相同才采纳 | 走子动画的中间态里棋子停在半路，位置不是任何合法点位，但识别结果"错得很合理"，会一路走到引擎。 |
| 这条门槛**可切成「单帧即采」** | 多等一个 700ms 间隔是能感觉到的，有人宁可按快。切成单帧后判据只剩「合法 + 能由上一帧走一步得到」（各给一格容忍），代价是动画中间态偶尔会闪一个错着法。面板第四排 / 主界面「采纳方式」可切。 |
| 盘面没变就**不重算** | 一次搜索是秒级，而画面在两步棋之间可能几十秒不动。不判这个，CPU 和电全烧在重复算同一个局面上。 |
| 走子方靠"哪些格子空了"推 | 识别只能看到盘面。「刚有一方走过」→ 空出来的格子上的子属于哪方，走的就是哪方。变化超过 6 格视为换局面，不推断。面板里还有 自动/轮红/轮黑 三态可手动纠正。 |
| 送引擎前过一道 `BoardSanity` | 皮卡鱼对不可能的局面不是给个错着，是 `CRITICAL ERROR: Unsupported position` 然后退出进程。 |

### 验证到哪一步

- **36 个 JVM 单测全过**（新增 `SideInferenceTest` 6 个、`BoardSanityTest` 9 个）
- `assembleDebug` 通过，APK **88.5MB**（模型 27MB + NNUE 51MB + onnxruntime 17MB）
- **没在真机上跑过** —— 开发机没有连设备。实机第一件事看三条日志：
  `adb logcat -s XiangqiScreenshot`（抓帧）、`XiangqiPanel`（识别/分析耗时）、`XiangqiEngine`（引擎启动）

顺手修掉一个数据 bug：`truth.tsv` 的 FEN 尾部是 `... w w`（`to_fen()` 自带侧别，
建 GT 时又加了一次），喂给引擎会直接报 `Unsupported position`。49 行已改。
